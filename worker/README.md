# Сервер уведомлений

Cloudflare Worker, который присылает push-уведомления о высоком шансе увидеть сияние, **даже когда приложение закрыто**. Сайт сам «проснуться» не может, поэтому раз в 10 минут это делает сервер: смотрит Kp (NOAA) и облачность (Open-Meteo) для точек, на которые есть подписчики, считает вердикт и при переходе в «Высокий» отправляет push.

Без этого сервера сайт работает как раньше: уведомления приходят, пока приложение открыто.

## Как устроено

```
браузер ──subscribe──▶ worker (D1) ◀──cron каждые 10 мин── NOAA + Open-Meteo
                          │
                          └─push (пустой, с подписью VAPID)──▶ push-сервис браузера ──▶ service worker
                                                                                             │
                                             POST /message (забрать текст) ◀─────────────────┘
```

- **Вердикт считает общее ядро [`core.js`](../core.js)** — тот же файл, что и на сайте. Уведомление не может разойтись с тем, что человек увидит в приложении; это проверяется тестом `tools/parity.test.mjs` на ~970 тыс. комбинаций и на реальной высоте Солнца в течение всего года.
- **Push пустой, без полезной нагрузки.** Не нужно шифровать сообщение (RFC 8291), а значит, нет целого класса тихих ошибок, когда push принят сервисом, но браузер не смог расшифровать. Текст уведомления service worker запрашивает у сервера сам; если сервер недоступен, покажется общее уведомление — браузеры требуют показывать уведомление на каждый push.
- **База — D1 (SQLite).** У worker'а на бесплатном тарифе не больше 50 внешних запросов за запуск, а D1 отдаёт всех подписчиков одним запросом.

## Когда приходит уведомление

Правила те же, что у уведомлений на сайте:

- при **переходе** вердикта точки в «Высокий», а не на каждом проходе, пока он держится;
- не чаще раза в 3 часа на человека;
- первое наблюдение за точкой — только точка отсчёта: «высокий», который уже идёт, никого не будит;
- подписавшийся во время «высокого» получает уведомление только о следующем;
- при неполных данных (недоступен NOAA или Open-Meteo, Kp старше 4 часов) проход пропускается целиком — иначе пропуск выглядел бы как «средний», а следующий проход — как переход;
- приложение открыто и в фокусе — уведомление не показывается (решает service worker).

Если подписчиков больше 35, рассылка растягивается на несколько проходов по 10 минут (лимит внешних запросов), никто не получает дважды.

## API

| Запрос | Что делает |
|---|---|
| `POST /subscribe` `{endpoint, point, lang?, quiet?, tz?}` | оформить подписку, сменить точку, язык уведомлений (`ru`, `en`, `zh`) или тихие часы: `quiet: {from, to}` — окно в часах 0–23 (может переходить через полночь), `quiet: null` — выключить, `tz` — пояс IANA, по которому оно считается. Не присланное остаётся прежним; негодное игнорируется |
| `POST /unsubscribe` `{endpoint}` | удалить подписку |
| `POST /message` `{endpoint}` | текст последнего уведомления (забирает service worker) |
| `POST /test` `{endpoint, delay?}` | пробное уведомление; задержка до 20 с, чтобы успеть закрыть приложение; не чаще раза в 20 с |
| `GET /health` | доступность и пульс: `{ok, lastCheck, outcome}` — когда и чем закончилась последняя проверка по расписанию (`ok`, `no_subs`, `no_kp`, `no_cloud`, `error`) |

Запросы принимаются только с адресов из `ALLOWED_ORIGINS`. Адрес подписки принимается только от известных push-сервисов (FCM, Mozilla, Apple, Windows): иначе worker можно было бы использовать для рассылки запросов куда угодно. Потолок — 5000 подписок.

## Приватность

Сервер хранит адрес подписки браузера, выбранную точку, язык уведомлений, тихие часы и часовой пояс — больше ничего: ни имён, ни почты, ни координат человека. Адрес подписки — секрет (по нему можно слать push), поэтому он не попадает ни в журналы, ни в ответы API. Выключение уведомлений удаляет запись; недействительные подписки (ответ 404 или 410 push-сервиса) удаляются автоматически.

## Развёртывание

Нужен бесплатный аккаунт на [cloudflare.com](https://dash.cloudflare.com/sign-up) и Node.js 18+.

```bash
cd worker
npm install
npx wrangler login                                  # откроет браузер, вход выполняете вы
```

**1. База данных**

```bash
npx wrangler d1 create aurora-push                  # выведет database_id
```

`database_id` впишите в `wrangler.toml`, затем создайте таблицы:

```bash
npx wrangler d1 execute aurora-push --remote --file schema.sql
```

**2. Ключи VAPID**

```bash
node scripts/generate-vapid.mjs ~/aurora-push-vapid.txt
```

Закрытый ключ записывается в файл (в терминал не выводится) — храните его вне репозитория. Напечатанный **открытый** ключ впишите в `VAPID_PUBLIC` в `wrangler.toml` и в `vapidPublicKey` в [`config.js`](../config.js). Закрытый — в секрет worker'а:

```bash
npx wrangler secret put VAPID_PRIVATE_KEY           # вставьте содержимое файла
```

> Не теряйте закрытый ключ и не меняйте его без нужды: подписки, оформленные со старым ключом, перестанут работать, и всем придётся включить уведомления заново.

**3. Публикация**

```bash
npx wrangler deploy                                 # выведет адрес вида https://aurora-push.<аккаунт>.workers.dev
```

Адрес впишите в `pushApi` в [`config.js`](../config.js), поднимите `CACHE_VERSION` в [`sw.js`](../sw.js) и опубликуйте сайт. Пока в `config.js` пусто, блок «Уведомления при закрытом приложении» на сайте скрыт.

**4. Проверка**

На вкладке «Уведомления» включите уведомления, нажмите «Через 20 секунд» и закройте приложение совсем: через 20 секунд уведомление придёт с сервера. Журнал worker'а: `npx wrangler tail`.

### Пульс

Каждый проход по расписанию записывает в таблицу `heartbeat` (одна строка) время и итог: `ok`, `no_subs` (некого будить — это норма), `no_kp` и `no_cloud` (NOAA или Open-Meteo не ответили, проход пропущен), `error`. `/health` отдаёт их, а страница показывает на вкладке «Настройки»: «сервер проверял условия 4 минуты назад», а если проверок не было больше 30 минут (три пропуска подряд) — предупреждение, что уведомления могут не прийти. Так видно, что cron не умер молча. Запись пульса не мешает проверке: если таблицы нет (база до миграции), проход идёт как раньше, а `/health` отвечает с `lastCheck: null`.

Для развёрнутой базы таблицу создают один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS heartbeat (id INTEGER PRIMARY KEY CHECK (id = 1), at INTEGER NOT NULL, outcome TEXT NOT NULL)"
npx wrangler deploy
```

### Запасной путь к Open-Meteo

`GET /meteo?<параметры /v1/forecast>` — тот же ответ Open-Meteo через сервер (`src/meteo.js`). Страница идёт сюда, только если прямой запрос не прошёл: сеть или VPN не пускает к `api.open-meteo.com`, адрес выбрал суточный лимит (ответ 429 приходит без CORS-заголовков, и браузер видит «нет соединения»). Не открытый прокси: только `/v1/forecast`, только нужные параметры с проверкой значений (до 100 точек), только со страницы сайта (`Origin` из `ALLOWED_ORIGINS`, иначе 403). Ответы хранятся в памяти worker'а 10 минут; ошибки не кэшируются, 429 источника передаётся как 429.

### Проверка прогноза

Вечером сервер записывает, какой шанс на ночь обещает прогноз для каждой из семи точек, а утром — каким он оказался; `GET /verify` отдаёт итог за последние 60 ночей (`{ nights, total, exact, offByOne, offByTwo, promised: { high: { n, high, mid, low }, … } }`, кэш на час). Код — `src/verify.js`.

- **Правила** — те же, что у окна наблюдения на сайте: ночь — первый тёмный отрезок (Солнце ниже −6°), уровень часа — `verdictLevel` из ядра, уровень ночи — лучший из часов.
- **Прогноз** (первый проход с 17:00 до 20:00 МСК): Kp — прогноз NOAA (`noaa-planetary-k-index-forecast.json`), облачность — прогноз ICON-EU на сутки для семи точек одним запросом.
- **Факт** (с 08:00 до 12:00 МСК следующего дня): Kp — измеренные строки (`observed`, `estimated`) того же файла, облачность — та же модель за прошедшие часы (`past_days=1`). Ночь сверяется, только когда все её тёмные часы уже прошли; в полярную ночь это около 10:30 МСК.
- Шаг — внутри проверки по расписанию, от подписчиков не зависит; нет данных — следующий проход попробует снова. Сбой не мешает рассылке. Летом (белые ночи) записей нет.

Для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS verify (night TEXT NOT NULL, point TEXT NOT NULL, forecast TEXT NOT NULL, actual TEXT, from_ms INTEGER NOT NULL, PRIMARY KEY (night, point))"
npx wrangler deploy
```

### О чём сообщать: средний шанс и «небо откроется»

Подписчик выбирает на сайте (блок «О чём сообщать»), страница присылает выбор в `/subscribe` (`level: high | mid`, `sky: true | false`; не присланное не меняется). Код — `src/options.js`, после основной рассылки; сбой здесь её не трогает.

- **`min_level = mid`** — уведомление уже при переходе из «низкого» в «средний или выше». Начало такого эпизода хранится в `point_state.mid_since`; первое наблюдение — точка отсчёта, как у «высокого». Лимит общий с основными уведомлениями — раз в 3 часа (`last_sent`); кто в этот проход уже получил «высокий», второго сообщения не получит.
- **`sky = 1`** — «небо скоро откроется»: сейчас сплошные облака (балл облачности 0), Kp дотягивает до порога точки, а почасовой прогноз (тот же запрос к Open-Meteo, `forecast_hours=4`) обещает облачность не больше 50 % в тёмный час в ближайшие 3 часа. Время в тексте — по поясу подписчика (или МСК). Не чаще раза в 8 часов (`last_sky`) и не раньше чем через час после уведомления о сиянии; тихие часы соблюдаются.

Для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN min_level TEXT NOT NULL DEFAULT 'high'"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN sky INTEGER NOT NULL DEFAULT 0"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN last_sky INTEGER NOT NULL DEFAULT 0"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE point_state ADD COLUMN mid_since INTEGER NOT NULL DEFAULT 0"
npx wrangler deploy
```

### Отметки «Вижу сияние»

`POST /report { point, strength }` — очевидец отмечает, что видит сияние у точки (`faint` — слабое, `bright` — яркое); `GET /reports` — сводка за последний час по точкам: `{ window, total, points: { id: { count, bright, last } } }`, кэшируется на минуту. Код — `src/reports.js`.

- **Без текста и фото** — модерировать нечего.
- **Против накруток**: отметка принимается, только если у точки темно (днём сияния не видно); с одного адреса — не чаще раза в 30 минут и не больше 6 в сутки (сутки по UTC); всего — не больше 300 в час.
- **Обезличивание**: адрес (IP) не хранится — только 16 знаков HMAC от адреса и даты с секретным ключом (`REPORT_SECRET`, если задан, иначе закрытый ключ VAPID). Без ключа адрес по ним не подобрать, а на следующие сутки значение уже другое. В сводку попадают только числа.
- **Срок**: отметки старше суток удаляет проход по расписанию.
- **До миграции**: сводка пустая, отметка отвечает `503 unavailable`, остальное работает как раньше.

Для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS reports (id INTEGER PRIMARY KEY AUTOINCREMENT, point TEXT NOT NULL, strength TEXT NOT NULL, at INTEGER NOT NULL, who TEXT NOT NULL)"
npx wrangler d1 execute aurora-push --remote --command "CREATE INDEX IF NOT EXISTS reports_at ON reports(at)"
npx wrangler d1 execute aurora-push --remote --command "CREATE INDEX IF NOT EXISTS reports_who ON reports(who, at)"
npx wrangler deploy
```

### Ранний сигнал: Bz повернул на юг

Kp — усреднение за три часа и запаздывает. Магнитное поле солнечного ветра (Bz), измеренное спутниками в точке L1, опережает сияние на 30–60 минут. Поэтому, кроме уведомления о высоком шансе, сервер шлёт ранний сигнал «сияние может начаться в ближайший час» (`src/bz.js`).

- **Источник** — сводка NOAA `products/summary/solar-wind-mag-field.json` (60 байт, текущий Bz). Поминутный ряд весит 1,6 МБ — бесплатному worker'у раз в 10 минут его не разобрать. Как долго поле держится южным, сервер считает сам между проходами и хранит в таблице `sw_state`.
- **Когда**: Bz ≤ −10 нТл два прохода подряд (10 минут) или ≤ −5 нТл три прохода (20 минут) — те же пороги, что у карточки солнечного ветра на сайте. Один отсчёт не считается: поле может мигнуть. Пропуск данных обрывает эпизод.
- **Где**: в точке темно и облака не сплошные (балл облачности ≥ 1). Kp не нужен — смысл сигнала в том, что Kp ещё не вырос. Если уровень уже «высокий», ранний сигнал не шлётся: основное уведомление говорит то же самое.
- **Кому и как часто**: подписчикам этой точки, оформившим подписку до начала эпизода; один раз на эпизод и не чаще раза в 6 часов (`last_bz`), не раньше чем через час после основного уведомления, с учётом тихих часов. Лимит основных уведомлений (`last_sent`) не расходуется.
- **Устойчивость**: сбой раннего сигнала (например, база ещё без новой таблицы) не мешает основной рассылке.

Для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS sw_state (id INTEGER PRIMARY KEY CHECK (id = 1), bz REAL, at INTEGER NOT NULL, south_since INTEGER NOT NULL DEFAULT 0)"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN last_bz INTEGER NOT NULL DEFAULT 0"
npx wrangler deploy
```

### Тихие часы

В таблице `subs` появились колонки `quiet_from`, `quiet_to` и `tz`. Получатель в тихих часах пропускается при рассылке (час считается по его поясу общей функцией `inQuietHours` из `core.js`). Ничего не теряется: пока «высокий» держится, пропущенный остаётся подходящим и получает уведомление первым проходом после окончания окна. Пропущенные не расходуют лимит отправок за проход; пробное уведомление приходит всегда. Негодный пояс или окно не заглушают уведомление.

Для развёрнутой базы колонки добавляют один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN quiet_from INTEGER"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN quiet_to INTEGER"
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN tz TEXT"
npx wrangler deploy
```

### Обновление с версии без языков

В таблице `subs` появилась колонка `lang` (язык уведомлений). Для уже развёрнутой базы её добавляют один раз, до выкладки нового кода worker'а; существующие подписки остаются русскими, пока страница не пришлёт язык:

```bash
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN lang TEXT NOT NULL DEFAULT 'ru'"
npx wrangler deploy
```

Порядок важен: новый код читает колонку, и без неё проход по расписанию упал бы. Старая страница язык не присылает — worker принимает и такие запросы.

## Локальная разработка

```bash
npx wrangler d1 execute aurora-push --local --file schema.sql
node scripts/generate-vapid.mjs ./.dev-vapid.txt    # только для локальной проверки
```

В файл `.dev.vars` (он в `.gitignore`) положите две строки — значение **без кавычек**:

```
VAPID_PRIVATE_KEY=<содержимое .dev-vapid.txt>
VAPID_PUBLIC=<открытый ключ из вывода>
```

```bash
npx wrangler dev --test-scheduled                   # http://localhost:8787
curl "http://localhost:8787/cdn-cgi/handler/scheduled"   # запустить проверку по расписанию
```

## Тесты

```bash
npm test                                            # 110 тестов, работают без сети и без аккаунта
node --test ../tools/*.test.mjs                     # клиент, service worker, согласие с сайтом
```

База в тестах — встроенный в Node SQLite (D1 — это SQLite), NOAA, Open-Meteo и push-серверы заменены подделками, которые записывают все обращения. Тесты проверены мутациями: намеренно ломаются 28 мест кода (порог перехода, пауза в 3 часа, лимит отправок, проверка адресов, срок подписи и другие), и каждая порча должна ронять хотя бы один тест.

## Что проверено только в настоящей среде

Часть ошибок Node-тесты увидеть не могут, поэтому worker запускался в настоящем `wrangler dev` (workerd): так нашлось, что главный модуль не может экспортировать ничего, кроме обработчиков (поэтому логика лежит в `api.js` и `check.js`, а `index.js` — тонкая точка входа), и что JSON внутри переменной окружения ненадёжен (поэтому секрет — короткая строка base64url). В той же среде проверены подпись VAPID и настоящий ответ push-сервиса (HTTP 410 на несуществующую подписку).

Не проверено: доставка настоящего push на устройство — для этого нужны развёрнутый worker и живая подписка.
