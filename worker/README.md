# Сервер уведомлений

Cloudflare Worker, который присылает push-уведомления о высоком шансе увидеть сияние, **даже когда приложение закрыто**. Сайт сам «проснуться» не может, поэтому раз в 5 минут это делает сервер: смотрит Kp (NOAA) и облачность (Open-Meteo) для точек, на которые есть подписчики, считает вердикт и при переходе в «Высокий» отправляет push.

Без этого сервера сайт работает как раньше: уведомления приходят, пока приложение открыто.

## Как устроено

```
браузер ──subscribe──▶ worker (D1) ◀──cron каждые 5 мин─── NOAA + Open-Meteo
                          │
                          └─push (пустой, с подписью VAPID)──▶ push-сервис браузера ──▶ service worker
                                                                                             │
                                             POST /message (забрать текст) ◀─────────────────┘
```

- **Вердикт считает общее ядро [`core.js`](../core.js)** — тот же файл, что и на сайте. Уведомление не может разойтись с тем, что человек увидит в приложении; это проверяется тестом `tools/parity.test.mjs` на ~970 тыс. комбинаций и на реальной высоте Солнца в течение всего года.
- **Push пустой, без полезной нагрузки.** Не нужно шифровать сообщение (RFC 8291), а значит, нет целого класса тихих ошибок, когда push принят сервисом, но браузер не смог расшифровать. Текст уведомления service worker запрашивает у сервера сам; если сервер недоступен, покажется общее уведомление — браузеры требуют показывать уведомление на каждый push.
- **База — D1 (SQLite).** У worker'а на бесплатном тарифе не больше 50 внешних запросов за запуск, а D1 отдаёт всех подписчиков одним запросом.

## Когда приходит уведомление

Правила те же, что у уведомлений на сайте:

- при **переходе** вердикта точки в «Высокий», а не на каждом проходе, пока он держится;
- не чаще раза в 3 часа на человека;
- первое наблюдение за точкой — только точка отсчёта: «высокий», который уже идёт, никого не будит;
- подписавшийся во время «высокого» получает уведомление только о следующем;
- при неполных данных (недоступен NOAA или Open-Meteo, Kp старше 4 часов) проход пропускается целиком — иначе пропуск выглядел бы как «средний», а следующий проход — как переход;
- приложение открыто и в фокусе — уведомление не показывается (решает service worker).

Если подписчиков больше 35 (или меньше, если проход уже потратил часть лимита в 50 внешних запросов на данные, сверку и мониторинг), рассылка растягивается на несколько проходов по 5 минут, никто не получает дважды.

Активность — как у вердикта на сайте (`activityScore` в `core.js`): лучший из признаков — Kp сейчас и максимум за час, Hp30 (получасы, закончившиеся не раньше часа назад), OVATION в поле зрения точки и отметки «Вижу сияние». Южный Bz в уровень не входит — у него свой ранний сигнал. OVATION сервер берёт из урезанной копии в `noaa_cache`, которую со сдвигом на 5 минут обновляет второе расписание (`refreshOvation`): разбор полного файла в общем проходе не уложился бы в 10 мс процессора. В навигационных сумерках (Солнце от −6° до −12°) «высокий» ставится только при сильной активности (балл 3): яркое сияние видно и тогда, а иначе вечернее уведомление ждало бы полной темноты.

> **Выкладывайте worker только из актуального `main`** (`git fetch` и `git status -sb` перед `wrangler deploy`). 13.10.2026 его выложили из старой рабочей копии, и до 22.10 сервер считал уровень только по текущему Kp: без Kp за час, Hp30 и отметок очевидцев. Уведомления приходили позже, чем сайт показывал «высокий», а `/hit` не работал.

## API

| Запрос | Что делает |
|---|---|
| `POST /subscribe` `{endpoint, point, lang?, quiet?, tz?}` | оформить подписку, сменить точку, язык уведомлений (`ru`, `en`, `zh`) или тихие часы: `quiet: {from, to}` — окно в часах 0–23 (может переходить через полночь), `quiet: null` — выключить, `tz` — пояс IANA, по которому оно считается. Не присланное остаётся прежним; негодное игнорируется |
| `POST /unsubscribe` `{endpoint}` | удалить подписку |
| `POST /message` `{endpoint}` | текст последнего уведомления (забирает service worker) |
| `POST /test` `{endpoint, delay?}` | пробное уведомление; задержка до 20 с, чтобы успеть закрыть приложение; не чаще раза в 20 с |
| `GET /health` | доступность и пульс: `{ok, lastCheck, outcome}` — когда и чем закончилась последняя проверка по расписанию (`ok`, `no_subs`, `no_kp`, `no_cloud`, `error`) |

Запросы принимаются только с адресов из `ALLOWED_ORIGINS`. Адрес подписки принимается только от известных push-сервисов (FCM, Mozilla, Apple, Windows): иначе worker можно было бы использовать для рассылки запросов куда угодно. Потолок — 5000 подписок.

## Приватность

Сервер хранит адрес подписки браузера, выбранную точку, язык уведомлений, тихие часы и часовой пояс — больше ничего: ни имён, ни почты, ни координат человека. Адрес подписки — секрет (по нему можно слать push), поэтому он не попадает ни в журналы, ни в ответы API. Выключение уведомлений удаляет запись; недействительные подписки (ответ 404 или 410 push-сервиса) удаляются автоматически.

## Развёртывание

Нужен бесплатный аккаунт на [cloudflare.com](https://dash.cloudflare.com/sign-up) и Node.js 18+.

```bash
cd worker
npm install
npx wrangler login                                  # откроет браузер, вход выполняете вы
```

**1. База данных**

```bash
npx wrangler d1 create aurora-push                  # выведет database_id
```

`database_id` впишите в `wrangler.toml`, затем создайте таблицы:

```bash
npx wrangler d1 execute aurora-push --remote --file schema.sql
```

**2. Ключи VAPID**

```bash
node scripts/generate-vapid.mjs ~/aurora-push-vapid.txt
```

Закрытый ключ записывается в файл (в терминал не выводится) — храните его вне репозитория. Напечатанный **открытый** ключ впишите в `VAPID_PUBLIC` в `wrangler.toml` и в `vapidPublicKey` в [`config.js`](../config.js). Закрытый — в секрет worker'а:

```bash
npx wrangler secret put VAPID_PRIVATE_KEY           # вставьте содержимое файла
```

> Не теряйте закрытый ключ и не меняйте его без нужды: подписки, оформленные со старым ключом, перестанут работать, и всем придётся включить уведомления заново.

**3. Публикация**

```bash
npx wrangler deploy                                 # выведет адрес вида https://aurora-push.<аккаунт>.workers.dev
```

Адрес впишите в `pushApi` в [`config.js`](../config.js), поднимите `CACHE_VERSION` в [`sw.js`](../sw.js) и опубликуйте сайт. Пока в `config.js` пусто, блок «Уведомления при закрытом приложении» на сайте скрыт.

**4. Проверка**

На вкладке «Уведомления» включите уведомления, нажмите «Через 20 секунд» и закройте приложение совсем: через 20 секунд уведомление придёт с сервера. Журнал worker'а: `npx wrangler tail`.

### Пульс

Каждый проход по расписанию записывает в таблицу `heartbeat` (одна строка) время и итог: `ok`, `no_subs` (некого будить — это норма), `no_kp` и `no_cloud` (NOAA или Open-Meteo не ответили, проход пропущен), `error`. `/health` отдаёт их, а страница показывает на вкладке «Настройки»: «сервер проверял условия 4 минуты назад», а если проверок не было больше 30 минут (три пропуска подряд) — предупреждение, что уведомления могут не прийти. Так видно, что cron не умер молча. Запись пульса не мешает проверке: если таблицы нет (база до миграции), проход идёт как раньше, а `/health` отвечает с `lastCheck: null`.

### Журнал проходов и сверка с очевидцами

Каждый проход пишет в таблицу `alert_log` строку на точку (`src/journal.js`): Kp, Kp за час, Hp30 и сколько минут назад закончился его последний получас, OVATION в поле зрения, Bz, облачность, высоту Солнца, баллы, итоговый уровень, по какому признаку он получен, отметки «Вижу сияние» за последний час и сколько уведомлений ушло (о высоком шансе, ранних Bz, прочих). Около тысячи строк в сутки, хранятся 90 дней. Сбой записи рассылку не трогает.

Владельцу в боте — `/timing`: за 14 ночей по точкам — когда начался «высокий», когда ушло первое уведомление, первый ранний сигнал Bz, когда появились и прекратились отметки очевидцев, и итог: сколько раз уведомление опередило очевидцев и сколько опоздало (медианы в минутах), сколько раз сияние видели, а уведомления не было. По этим числам, а не на глаз, стоит менять пороги.

Миграция для базы, созданной до журнала:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS alert_log (at INTEGER NOT NULL, point TEXT NOT NULL, level TEXT NOT NULL, ks INTEGER, cs INTEGER, source TEXT, kp REAL, kp_hour REAL, hp30 REAL, hp30_age INTEGER, ovation REAL, bz REAL, bz_level TEXT, cloud INTEGER, alt REAL, seen INTEGER NOT NULL DEFAULT 0, sent_high INTEGER NOT NULL DEFAULT 0, sent_bz INTEGER NOT NULL DEFAULT 0, sent_other INTEGER NOT NULL DEFAULT 0, PRIMARY KEY (at, point))"
```

Для развёрнутой базы таблицу создают один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS heartbeat (id INTEGER PRIMARY KEY CHECK (id = 1), at INTEGER NOT NULL, outcome TEXT NOT NULL)"
npx wrangler deploy
```

### Telegram-бот для посетителей

Тот же бот, что пишет владельцу о сбоях, рассылает посетителям уведомления о сиянии (`src/telegram.js`). На сайте он намеренно не упоминается — о нём рассказывают сами.

- **Подписка:** `/start` → точка кнопками (или ссылка `t.me/<бот>?start=<точка>`, например `?start=teriberka`). Язык — по языку Telegram-клиента (ru, en, zh; остальные — английский).
- **Команды:** `/now` — уровень шанса у своей точки по последней проверке сервера, `/settings` — точка, порог («только высокий» или «и средний»), ранний сигнал о Bz, `/stop` — отписаться. В меню команд Telegram — на трёх языках.
- **Уведомления** — те же, что push в браузере, и по тем же правилам: переход в «высокий» (или в «средний», если выбрано), ранний сигнал «Bz повернул на юг»; не чаще раза в 3 часа, ранний сигнал — раз в 6 часов, не раньше чем через час после уведомления о сиянии. Смена точки начинает отсчёт заново. Бот заблокирован или чат удалён — подписка удаляется.
- **Webhook:** сообщения от Telegram приходят на `POST /telegram`. Адрес (`PUBLIC_URL` в `wrangler.toml` + `/telegram`), меню команд и имя бота сервер регистрирует сам первым проходом по расписанию после появления токена. Подлинность запроса — заголовок `X-Telegram-Bot-Api-Secret-Token`, выведенный из токена (HMAC): отдельный секрет не нужен, подделать без токена нельзя. Группы и каналы бот не обслуживает.
- **Хранится** только номер чата, точка, язык и настройки (таблица `tg_subs`). Точки подписчиков Telegram проверяются вместе с точками подписчиков в браузере.

Таблицы для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS tg_subs (chat_id TEXT PRIMARY KEY, point TEXT NOT NULL, lang TEXT NOT NULL DEFAULT 'ru', min_level TEXT NOT NULL DEFAULT 'high', bz INTEGER NOT NULL DEFAULT 1, created INTEGER NOT NULL, last_sent INTEGER NOT NULL DEFAULT 0, last_bz INTEGER NOT NULL DEFAULT 0, fails INTEGER NOT NULL DEFAULT 0)"
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS meta (key TEXT PRIMARY KEY, value TEXT)"
```

### Мониторинг источников и оповещение владельцу

Каждый проход по расписанию (`src/monitor.js`) проверяет, что источники отвечают и данные свежие: Kp у NOAA (измерение не старше 30 минут), солнечный ветер (спутники передавали не позже 45 минут назад), Open-Meteo (в ответе есть облачность) и сам сайт. Сбой дольше 20 минут (два прохода подряд — одна осечка не повод) — сообщение владельцу в Telegram, пока сбой длится — напоминание раз в 6 часов, источник вернулся — «✅ Снова работает» с длительностью сбоя. Состояние — в таблице `monitor`; сообщение считается отправленным, только если Telegram его принял, иначе уйдёт следующим проходом.

Бот и чат владельца — секреты worker'а, в репозитории их нет. Задаются один раз:

```bash
npx wrangler secret put TELEGRAM_TOKEN        # токен бота от @BotFather
npx wrangler secret put TELEGRAM_OWNER_CHAT   # ваш числовой id в Telegram (его покажет @userinfobot)
```

Пока секретов нет, мониторинг всё равно ведёт состояние, но ничего не отправляет. Таблица для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS monitor (source TEXT PRIMARY KEY, down_since INTEGER NOT NULL, notified_at INTEGER NOT NULL DEFAULT 0, detail TEXT)"
```

### Статистика посещений и журнал ошибок (владельцу в боте)

Страница подключает `track.js` сразу после `config.js`.

- **Посещения** (`POST /hit`, `src/stats.js`): раз за загрузку, через 3 секунды после неё — язык, телефон или компьютер, открыто ли как приложение, первый ли визит с устройства, хост сайта, с которого пришли. Без cookies и идентификаторов: посетитель за сутки — HMAC от адреса, браузера и даты (адрес не хранится, на следующие сутки отпечаток другой). Таблица `visits`, хранится 120 дней. Считаются только визиты с `https://auroramurmansk.ru` — локальная разработка статистику не портит.
- **Ошибки** (`POST /bug`, `src/bugs.js`): необработанные ошибки страницы (не больше 5 за загрузку, без ошибок расширений и сетевых сбоев), сбои самого сервера (проход по расписанию, запрос, webhook бота) и сообщения посетителей боту `/bug <что не так>` (не больше 5 в сутки с чата). Одинаковые склеиваются по отпечатку (текст без чисел, файл, строка) со счётчиком. Таблица `bugs`.
- **Владельцу** (чат `TELEGRAM_OWNER_CHAT`; в меню команд — только у него): `/stats` — сегодня, вчера, 7 и 30 дней, по дням, доли новых, телефонов и приложения, языки, источники, число подписчиков; `/bugs` — открытые ошибки с кнопками «подробно», «исправлено», «не важно». О новых ошибках сервер пишет сам ближайшим проходом (все новые — одним сообщением, не больше 30 новых в час). Исправленная ошибка, повторившаяся в более новой версии сайта, открывается снова. Каждое утро после 9:00 по Москве — сводка за вчера.

Таблицы для развёрнутой базы — один раз, до выкладки кода:

```bash
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS visits (day TEXT NOT NULL, who TEXT NOT NULL, views INTEGER NOT NULL DEFAULT 1, lang TEXT, mobile INTEGER NOT NULL DEFAULT 0, pwa INTEGER NOT NULL DEFAULT 0, fresh INTEGER NOT NULL DEFAULT 0, ref TEXT, ver TEXT, first_at INTEGER NOT NULL, last_at INTEGER NOT NULL, PRIMARY KEY (day, who))"
npx wrangler d1 execute aurora-push --remote --command "CREATE TABLE IF NOT EXISTS bugs (id INTEGER PRIMARY KEY AUTOINCREMENT, fp TEXT NOT NULL UNIQUE, kind TEXT NOT NULL, msg TEXT NOT NULL, src TEXT, line INTEGER, col INTEGER, stack TEXT, ver TEXT, ua TEXT, page TEXT, count INTEGER NOT NULL DEFAULT 1, first_at INTEGER NOT NULL, last_at INTEGER NOT NULL, status TEXT NOT NULL DEFAULT 'open', notified_at INTEGER NOT NULL DEFAULT 0)"
npx wrangler d1 execute aurora-push --remote --command "CREATE INDEX IF NOT EXISTS bugs_status ON bugs(status, last_at)"
```

### Данные NOAA для страницы

`GET /noaa/<имя>` — те же файлы NOAA в том же формате, но компактнее (`src/noaa.js`): `kp`, `kp-3h`, `kp-forecast`, `sw-mag`, `sw-speed`, `ovation`, `outlook`. Страница берёт данные NOAA сначала отсюда, а прямой запрос к NOAA — запасной путь.

- **Меньше трафика:** поминутный ряд солнечного ветра — последние 2 часа 10 минут всех спутников и только нужные поля (около 30 КБ вместо 1 МБ); OVATION — клетки вокруг области (долготы 17–53°, широты 55–80°, около 10 КБ вместо 900 КБ). Итоговые расчёты по вырезкам совпадают с расчётами по полным файлам — это проверяют тесты и проверено на живых данных.
- **Укладывается в лимит бесплатного worker'а** (10 мс процессора на запрос): тяжёлые файлы не разбираются целиком — нужный кусок вырезается поиском по строке, разбор занимает около 1 мс.
- **Память и запас:** ответы хранятся в памяти worker'а (от минуты для Kp и солнечного ветра до часа для прогноза на 27 дней). Если NOAA не отвечает, отдаётся последняя удачная копия не старше 6 часов с заголовком `X-Stale: 1` — страница видит её возраст по времени внутри данных.
- **Только со страницы сайта** (`Origin` из `ALLOWED_ORIGINS`), неизвестное имя — 404.
- **Лимит Cloudflare:** бесплатно — 100 000 запросов в сутки. Открытая круглые сутки вкладка делает около 1 700; если лимит кончится, страница сама перейдёт на прямые запросы к NOAA.

### Запасной путь к Open-Meteo

`GET /meteo?<параметры /v1/forecast>` — тот же ответ Open-Meteo через сервер (`src/meteo.js`). Страница идёт сюда, только если прямой запрос не прошёл: сеть или VPN не пускает к `api.open-meteo.com`, адрес выбрал суточный лимит (ответ 429 приходит без CORS-заголовков, и браузер видит «нет соединения»). Не открытый прокси: только `/v1/forecast`, только нужные параметры с проверкой значений (до 100 точек), только со страницы сайта (`Origin` из `ALLOWED_ORIGINS`, иначе 403). Ответы хранятся в памяти worker'а 10 минут; ошибки не кэшируются, 429 источника передаётся как 429.

`GET /metno/cloud?lat=&lon=`: общая облачность MET Norway на 48 часов: `{ model, hours: [[секунды UTC, %], …] }` (`src/metno.js`). Второе мнение для карточки облачности: страница сравнивает его с ICON-EU и, если модели расходятся на 40 п.п. и больше, пишет об этом. Координаты округляются до 0,01°, копия на место хранится 30 минут, поэтому в MET Norway уходит не больше одного запроса на место за полчаса. Только со страницы сайта, как и `/meteo`. Open-Meteo этот адрес не трогает и его лимит не расходует.

**Если Open-Meteo не отвечает совсем**, сервер берёт тот же прогноз у MET Norway (`src/metno.js`) и пересобирает ответ в формат Open-Meteo с пометкой `generator: "MET Norway"` — страница разбирает его как обычно и пишет в карточке облачности «Модель прогноза: MET Norway». Отдаётся только общая облачность: ярусы MET Norway противоречат её же общей облачности (см. раздел о выборе модели в README сайта), и страница посчитает по общей, как всегда делает без ярусов. Видимости у модели нет — есть доля тумана: при густом тумане видимость считается 500 м. Резерв — только для запросов до 10 точек и без прошлых дней: сетке облаков над картой (90 точек) и «Прошлым ночам» он не положен. Запросы к MET Norway идут с User-Agent сайта, как требуют их условия. Не ответил и MET Norway — отдаётся последняя удачная копия не старше 3 часов.

### Проверка прогноза

Вечером сервер записывает, какой шанс на ночь обещает прогноз для каждой из семи точек (уровень, наибольший Kp и наименьшая облачность за тёмные часы), а утром каким он оказался по измерениям и сколько разных устройств отметили сияние у точки за самый «людный» час ночи. `GET /verify` отдаёт итог за последние 30 дней (`{ days, nights, total, exact, offByOne, offByTwo, promised: { high: { n, high, mid, low }, … }, seen: { checked, confirmed, hit } }`, кэш на час). `seen.confirmed`: случаи с подтверждённым сиянием (3 устройства за час), `seen.hit`: из них вечерний прогноз был средним или высоким. Код в `src/verify.js`.

- **Правила** — те же, что у окна наблюдения на сайте: ночь — первый тёмный отрезок (Солнце ниже −6°), уровень часа — `verdictLevel` из ядра, уровень ночи — лучший из часов.
- **Прогноз** (первый проход с 17:00 до 20:00 МСК): Kp — прогноз NOAA (`noaa-planetary-k-index-forecast.json`), облачность — прогноз ICON-EU на сутки для семи точек одним запросом.
- **Факт** (с 08:00 до 12:00 МСК следующего дня): Kp — измеренные строки (`observed`, `estimated`) того же файла, облачность — та же модель за прошедшие часы (`past_days=1`). Ночь сверяется, только когда все её тёмные часы уже прошли; в полярную ночь это около 10:30 МСК.
- Шаг — внутри проверки по расписанию, от подписчиков не зависит; нет данных — следующий проход попробует снова. Сбой не мешает рассылке. Летом (белые ночи) записей нет.

Для развёрнутой базы — один раз, до выкладки кода:


Kp, облачность и очевидцы в сверке (октябрь 2026), один раз для развёрнутой базы. До этого сервер пишет и считает по-старому:

### О чём сообщать: средний шанс и «небо откроется»

Подписчик выбирает на сайте (блок «О чём сообщать»), страница присылает выбор в `/subscribe` (`level: high | mid`, `sky: true | false`; не присланное не меняется). Код — `src/options.js`, после основной рассылки; сбой здесь её не трогает.

- **`min_level = mid`** — уведомление уже при переходе из «низкого» в «средний или выше». Начало такого эпизода хранится в `point_state.mid_since`; первое наблюдение — точка отсчёта, как у «высокого». Лимит общий с основными уведомлениями — раз в 3 часа (`last_sent`); кто в этот проход уже получил «высокий», второго сообщения не получит.
- **`sky = 1`** — «небо скоро откроется»: сейчас сплошные облака (балл облачности 0), Kp дотягивает до порога точки, а почасовой прогноз (тот же запрос к Open-Meteo, `forecast_hours=4`) обещает облачность не больше 50 % в тёмный час в ближайшие 3 часа. Время в тексте — по поясу подписчика (или МСК). Не чаще раза в 8 часов (`last_sky`) и не раньше чем через час после уведомления о сиянии; тихие часы соблюдаются.

Для развёрнутой базы — один раз, до выкладки кода:

### Отметки «Вижу сияние»

`POST /report { point, strength, device }`: очевидец отмечает, что видит сияние у точки (`faint` слабое, `bright` яркое); `device` это случайный номер устройства, который сайт хранит у себя. `GET /reports`: сводка за последний час по точкам `{ window, total, confirm, points: { id: { count, devices, bright, last, confirmed } } }`, кэшируется на минуту. Код в `src/reports.js`.

- **Без текста и фото**, модерировать нечего.
- **Против накруток**: точка должна быть из списка области и у неё должно быть темно; с одного устройства у одной точки одна отметка в час; с одного IP не больше 4 в час и 12 в сутки (сутки по UTC); всего не больше 300 в час.
- **Подтверждение**: `confirmed` ставится, если за час отметили минимум с 3 разных устройств (`CONFIRM_DEVICES`). Только подтверждённые отметки поднимают шанс на сайте и в уведомлениях; иначе сайт показывает просто число.
- **Обезличивание**: IP и номер устройства не хранятся, только по 16 знаков HMAC с солью: от IP и даты (на следующие сутки значение другое) и от номера устройства. Соль берётся из `REPORT_SALT` (см. `.env.example`); для старых развёртываний запасной вариант: `REPORT_SECRET` или закрытый ключ VAPID. Без соли отметки не принимаются. В сводку попадают только числа.
- **Срок**: отметки старше суток удаляет проход по расписанию.
- **До миграции**: без таблицы сводка пустая, отметка отвечает `503 unavailable`; без колонки `dev` отметки принимаются по-старому, а устройством считается хеш IP.

Колонка `dev` для номера устройства (октябрь 2026), один раз для развёрнутой базы:

```bash
npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE reports ADD COLUMN dev TEXT"
npx wrangler d1 execute aurora-push --remote --command "CREATE INDEX IF NOT EXISTS reports_dev ON reports(dev, point, at)"
npx wrangler secret put REPORT_SALT
```

Для развёрнутой базы — один раз, до выкладки кода:


### Ранний сигнал: Bz повернул на юг

Kp — усреднение за три часа и запаздывает. Магнитное поле солнечного ветра (Bz), измеренное спутниками в точке L1, опережает сияние: ветер идёт до Земли 30–60 минут, и ещё нужно время, чтобы поле накопило энергию, — суббуря чаще всего начинается через 30–90 минут. Поэтому, кроме уведомления о высоком шансе, сервер шлёт ранний сигнал «сияние может начаться в ближайшие 1–2 часа» (`src/bz.js`).

- **Источник** — сводка NOAA `products/summary/solar-wind-mag-field.json` (60 байт, текущий Bz). Поминутный ряд весит 1,6 МБ — бесплатному worker'у раз в 5 минут его не разобрать. Как долго поле держится южным, сервер считает сам между проходами и хранит в таблице `sw_state`.
- **Когда**: Bz ≤ −10 нТл два прохода подряд (10 минут) или ≤ −5 нТл четыре прохода (30 минут). Пороги по Bz — те же, что у карточки солнечного ветра на сайте, а длительность умеренно южного поля строже (было 20 минут): умеренному полю нужно время, чтобы накопить энергию, и сигнал не должен приходить на короткий провал. Помогает ли это — видно в `/timing`. Один отсчёт не считается: поле может мигнуть. Пропуск данных обрывает эпизод.
- **Где**: в точке темно и облака не сплошные (балл облачности ≥ 1). Kp не нужен — смысл сигнала в том, что Kp ещё не вырос. Если уровень уже «высокий», ранний сигнал не шлётся: основное уведомление говорит то же самое.
- **Кому и как часто**: подписчикам этой точки, оформившим подписку до начала эпизода; один раз на эпизод и не чаще раза в 6 часов (`last_bz`), не раньше чем через час после основного уведомления, с учётом тихих часов. Лимит основных уведомлений (`last_sent`) не расходуется.
- **Устойчивость**: сбой раннего сигнала (например, база ещё без новой таблицы) не мешает основной рассылке.

Для развёрнутой базы — один раз, до выкладки кода:

```bash

npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN last_bz INTEGER NOT NULL DEFAULT 0"
npx wrangler deploy
```

### Тихие часы

В таблице `subs` появились колонки `quiet_from`, `quiet_to` и `tz`. Получатель в тихих часах пропускается при рассылке (час считается по его поясу общей функцией `inQuietHours` из `core.js`). Ничего не теряется: пока «высокий» держится, пропущенный остаётся подходящим и получает уведомление первым проходом после окончания окна. Пропущенные не расходуют лимит отправок за проход; пробное уведомление приходит всегда. Негодный пояс или окно не заглушают уведомление.

Для развёрнутой базы колонки добавляют один раз, до выкладки кода:

```bash

npx wrangler d1 execute aurora-push --remote --command "ALTER TABLE subs ADD COLUMN tz TEXT"
npx wrangler deploy
```

### Обновление с версии без языков

В таблице `subs` появилась колонка `lang` (язык уведомлений). Для уже развёрнутой базы её добавляют один раз, до выкладки нового кода worker'а; существующие подписки остаются русскими, пока страница не пришлёт язык:

```bash

```

Порядок важен: новый код читает колонку, и без неё проход по расписанию упал бы. Старая страница язык не присылает — worker принимает и такие запросы.

## Что проверено только в настоящей среде

Часть ошибок Node-тесты увидеть не могут, поэтому worker запускался в настоящем `wrangler dev` (workerd): так нашлось, что главный модуль не может экспортировать ничего, кроме обработчиков (поэтому логика лежит в `api.js` и `check.js`, а `index.js` — тонкая точка входа), и что JSON внутри переменной окружения ненадёжен (поэтому секрет — короткая строка base64url). В той же среде проверены подпись VAPID и настоящий ответ push-сервиса (HTTP 410 на несуществующую подписку).

Не проверено: доставка настоящего push на устройство — для этого нужны развёрнутый worker и живая подписка.
